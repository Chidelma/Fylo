Encryption & access

Two separate mechanisms, deliberately not merged: field-level encryption for confidentiality and POSTIX for per-record authorization. Each is opt-in, and each is honest about what it does not protect against.

Field encryption

Fields listed in a schema's $encrypted array are stored with AES-GCM. Equality queries still work through HMAC blind indexes, so a lookup never has to decrypt. 

{schemaCode}

Nested fields use a slash-separated path (payload/verifier), matching the index field-path format. A dotted path such as payload.verifier is accepted as a literal field name, matches nothing, and silently leaves the field unencrypted — if a field is not being encrypted, check the stored document first.

  • FYLO_ENCRYPTION_KEY must be at least 32 characters.
  • FYLO_CIPHER_SALT is recommended, and derives the blind index.
  • The cipher is process-global: one key for all collections.

Decryption is schema-driven and does not depend on write history. A read-only process loads a collection's $encrypted registration on its first read, so replicas, reporting jobs, and event-sourced replay decrypt correctly without writing first.

Reads fail closed. If a field the schema declares $encrypted cannot be decrypted — missing key, wrong key, a value that fails authentication, or a value stored before the field was encrypted — the operation fails with EDECRYPTFAILED naming the collection and field. FYLO never hands back a stored value as if it were plaintext when it cannot verify it.

The consequence: adding a field to $encrypted requires rewriting the documents that already hold a plaintext value for it.

Blind indexes leak frequency. An attacker with index access can count how often a value repeats without decrypting anything — that is the price of indexed equality on encrypted data, and it is a real one for low-cardinality fields.

POSTIX access control

POSTIX binds a POSIX UID, GID, and mode to individual records. FYLO applies chown and chmod and stores a portable descriptor in user.fylo.access — the permission lives on the file, not in a parallel table that could disagree with it.

The Node shim exposes the fluent .as() form. Every binary-backed shim carries the same identity as an access object on the machine request, documented under Machine protocol. 

{postixCode}

Any omitted identity retains the new file's native owner or group; omitting mode uses 0o600. Mode classes evaluate with normal POSIX precedence — owner bits for the owner UID, otherwise group bits for a member of the record GID, otherwise other bits. Membership does not fall through to other when the selected class denies the operation, so use 0o660 rather than 0o600 for a group-writable record.

Membership resolves from the host POSIX group database when only a UID is supplied. Applications with virtual users may additionally attach a trusted, request-scoped groups array over the local NDJSON boundary: 

{actorCode}

Treat stdin as a privileged application boundary. Derive both uid and groups from authenticated server state and never copy either from an end-user payload. The cached binary clears groups after each request and falls back to the host resolver when it is omitted.

FYLO does not authenticate the UID — it is an authorization claim your application supplies. Validate the caller before passing one. The FYLO process must also have permission to call chown, or the put fails atomically.

Denied direct operations throw FyloPermissionError with code === 'EACCES'; queries and SQL omit unreadable records rather than failing. A record written without .as() has no descriptor and remains open.

POSTIX is available only when the native binary and its binary-backed shims run on a POSIX host such as macOS or Linux. It is not a Windows authorization boundary, even though Windows supports FYLO's crash recovery. Browser, Explorer, and WebView-based mobile clients cannot call chown/chmod and therefore do not expose an equivalent boundary — keep them behind an authenticated native gateway when POSTIX enforcement is required.
