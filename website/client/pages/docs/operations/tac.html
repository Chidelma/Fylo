Native configuration

Environment variables consumed by the native Rust engine and its release tooling.

Environment

Variable Purpose Default
FYLO_ROOT Filesystem root for collections ./.fylo-data
FYLO_SCHEMA Directory containing JSON validation schemas —
FYLO_STRICT Validate documents with chex before writes —
FYLO_SHARD_WIDTH Trailing TTID characters used for newly created collection shards 1
FYLO_ENCRYPTION_KEY AES-GCM key for $encrypted fields (≥32 chars) —
FYLO_CIPHER_SALT Salt for blind index derivation —
FYLO_VERIFY_PROVENANCE Require signed artifact provenance during install —

Process model

The fylo executable is the only native engine. JavaScript and the other language packages are thin NDJSON clients and never open a root directly. Use --exclusive-root for long-lived processes that require one authoritative owner.

Binary-backed SDK applications can provide a .env path or native environment map when constructing the shim. Those values are scoped to the child process and override inherited values without modifying the host environment.

Resolution and isolation

FYLO resolves native configuration in this order:

  1. Explicit constructor and command-line arguments.
  2. The shim's optional .env file or environment map.
  3. Variables inherited from the host process.
  4. Engine defaults.

Each shim builds a fresh environment for its own child. This lets an application and its dependencies run independently configured FYLO roots in one process without changing global environment state. A null or nil map value removes an inherited key for that child.

.env syntax

# Blank lines and comments are ignored.
export FYLO_SCHEMA="/srv/app/schemas" # inline comments are supported
FYLO_STRICT=1
FYLO_SHARD_WIDTH=2

Values may be quoted or unquoted. Variable expansion, command substitution, and executable shell syntax are intentionally unsupported. Missing files and malformed entries fail before the native child starts.

Environment files and maps are administrator-controlled bootstrap input. Never derive either from a request, tenant setting, upload, or job payload: arbitrary keys can change PATH, dynamic-loader behavior, and which program starts. Use an absolute, administrator-controlled binary path, allowlist the required FYLO_* keys, and copy inherited values explicitly rather than forwarding an entire environment.

Keep populated files out of source control. Prefer a secret manager for credentials; when a file is required, add its exact name or pattern to the consuming application's ignore rules and make it owner-readable only (for example, chmod 600).
