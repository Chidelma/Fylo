Serverless queue

Durable topics, consumer groups, visibility leases, retries, and dead letters live inside the Rust engine. There is no queue daemon, cloud account, network dependency, or broker to operate.

Embedded and brokerless

Queue state lives beside the collections under the same FYLO root. Messages are immutable, claims are durable before their receipts are returned, and each consumer group advances independently. 

{layoutCode}

Serverless does not mean distributed multi-writer storage. FYLO still permits one owning engine process per root. Concurrent tasks share that process, and another process takes over only after the filesystem lease is released.

Seven machine operations

Operation Purpose
queuePublish Persist an immutable message, optionally with delayed availability and an idempotency key.
queueClaim Lease a bounded publication-ordered batch for one consumer group.
queueAck Complete one delivery using its opaque receipt.
queueNack Retry after a delay or move an exhausted delivery to that group's dead letters.
queueExtend Extend a live visibility lease for a long-running handler.
queueStats Read bounded topic and consumer-group counts.
queueDeadLetters Read the bounded dead-letter history for one group and topic.

The handshake advertises this contract as serverlessQueue.version === 1. A supervisor should reject a missing or unknown capability version before sending queue operations.

Direct control

Use the direct methods when the application needs custom settlement, lease extension, or a trusted diagnostic reason. Delivery is at least once, so every handler must be idempotent. 

{directCode}

Automatic consumers and general application code should persist a generic failure reason. Exception text can contain credentials or payload data and must not be copied into durable dead-letter state.

One-batch consumer decorators

Every native binary shim provides an idiomatic decorator, annotation, or callable wrapper. One invocation claims a bounded batch, calls the handler once per delivery, acknowledges successes, and negative-acknowledges failures. It returns claimed, acknowledged, retried, and deadLettered counts instead of hiding an infinite poll loop.

Retry and fencing rules

Event Rule
Publish response is lost Retry only with the same non-empty idempotency key, topic, and byte-equivalent JSON payload.
Claim response is lost Do not retry as if nothing happened. The persisted leases become visible after their timeout.
Worker becomes stale An expired or superseded opaque receipt cannot acknowledge, retry, or extend the delivery.
Handler fails Negative-acknowledge with a delay; exceeding maxAttempts dead-letters only that consumer group.
Worker exits Unacknowledged deliveries return automatically after the visibility timeout.

Resource limits

Topics and consumer groups are limited to 127 UTF-8 bytes. A stored message is at most 1 MiB; one claim returns at most 1,000 deliveries and 8 MiB. Each group retains at most 10,000 pending states and the 1,000 most recently acknowledged ID/receipt pairs. Claim and stats requests stop after 64 MiB of aggregate message-file scan work. Attempts cap at 100, visibility at 24 hours, delay at 30 days, and one dead-letter read at 1,000 entries. Exceeding a bound returns EQUEUE_LIMIT; invalid options or incompatible idempotency reuse return EQUEUE_INVALID; stale receipts return EQUEUE_RECEIPT.
