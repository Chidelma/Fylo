Version control

FYLO keeps a Git-shaped history of your documents, and it is on by default. Every write records a content-addressed snapshot, so you can branch a dataset, diff two points in time, and restore a collection to how it looked last Tuesday.

The commands

{cliCode}

status and diff compare document payloads only (docs/ and .deleted/), so rebuilt indexes, event journals, lock files, and mtime-only changes never create noisy diffs.

Auto-commit

put, patch, delete, and restore create commit snapshots after the local filesystem write succeeds. Failed writes and no-op mutations do not create empty commits.

Bulk operations coalesce: put.batch, patch.many, delete.many, and import each record one commit covering every document they touched. Prefer them for ingests.

Storage

Commit storage is content-addressed. Each document version is stored once as a deduplicated blob, so commits share unchanged bytes across history and branches instead of copying whole collections. Object hashes are verified before any restore or merge. 

{layoutCode}

main uses the root .collections tree. Other branches use hidden working trees under .fylo-vcs/branches/, so checkout -b isolates subsequent reads and writes without changing the base document layout.

Snapshots keep a full content-addressed copy of every raw file, which doubles disk and write bandwidth for large media collections. Exclude a collection from history at creation time when that trade is wrong: 

{unversionedCode}

Unversioned collections never appear in commits, diffs, or restores — their working files are the only copy, and restoreCommit leaves them untouched.

Restore and merge

restore-commit refuses to overwrite uncommitted working-tree changes unless --force is passed; commit snapshots themselves are immutable. merge supports fast-forward and three-way document-payload merges. If both sides changed the same TTID's payload differently, FYLO reports the conflicts and leaves the current branch untouched.

Restore and merge materialization runs inside a durable staging transaction. Startup deterministically rolls an interrupted swap backward or forward before any collection is opened — see Recovery & rebuild.
