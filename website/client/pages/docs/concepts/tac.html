Concepts

Ten words that mean something specific in FYLO. If you read one page before writing code, read this one — most confusion later is a word that meant something slightly different in the last store you used.

Root

A directory on a local filesystem, and the whole database. One process opens a root and owns it; there is no server in front of it and no protocol to reach it from elsewhere. Everything FYLO writes lives under that path — documents, indexes, journals, version history, locks.

The root comes from FYLO_ROOT, a constructor argument, or --root. Long-lived supervisors that need exactly one authoritative writer can take a kernel lease on it with --exclusive-root.

Collection and bucket

A collection holds documents — records that FYLO parses, indexes field by field, and can query. A bucket holds raw files — bytes FYLO stores verbatim and describes with derived metadata.

They are structurally identical: same directory layout, same index, same journal, same API. Only the value type differs, and only the top-level directory (.collections/ versus .buckets/) tells them apart on disk. A collection's kind is recorded once in its catalog descriptor, and names are unique across both namespaces, so db.<name> is never ambiguous.

Collections must be created explicitly before any read, write, or query. Use inspect() when you want a safe existence check — it returns exists: false rather than throwing.

Document

One JSON file. Its filename is the document's TTID, placed in a shard directory taken from the trailing characters of that TTID so no single directory grows unbounded. Trailing, because a TTID is time-ordered and its leading characters barely move — sharding on those put months of records in one directory. The width is a property of the collection, one character by default. A document may contain scalars, nested objects, and arrays of scalars.

It may not contain an array of objects at any depth. FYLO reads that shape as a sign the data wants to be its own collection, referenced by key, so that every field stays independently indexable. The write is rejected before any disk work with EARRAYOFOBJECTS and the offending field path.

TTID

A time-ordered identifier, generated by the ttid binary. It is the document's filename, its primary key, and its creation timestamp — the createdAt a document reports is derived from its TTID rather than stored separately.

Because TTIDs sort lexicographically in creation order, a directory listing is already a chronological listing, and pagination cursors can order by TTID binary text without a separate sort.

Index key

The index stores no payload. Each entry is a zero-byte key containing a object key — field path, kind, value, document ID — held in a sorted snapshot file that is memory-mapped for binary search, plus an append-only WAL that is compacted at 1 MiB. 

{keyCode}

The index is always local and always derived. No remote store is in the query path. If the index drifts — because a process wrote data files directly, or a copy tool dropped something — rebuild() reconstructs it from the documents.

Generation

A counter that tells readers whether they are looking at a settled collection. Every transactional mutation publishes an odd writing generation before it changes records, and the next even stable generation after it commits. Readers materialize against one stable generation and retry if it changes underneath them. 

{generationCode}

A writing state with no transaction in flight, or a corrupt state, is an operator incident — see Recovery & rebuild.

Transaction

A logical journal entry, written outside the collection tree under .fylo-transactions/ so it is never mistaken for a document, indexed or versioned. It records the operation, the commit phase, and a before-image manifest of everything needed to roll back.

On startup or first access, an active transaction is rolled back and one with a durable committed marker is rolled forward. Atomicity is per collection: there is no atomic multi-collection commit.

Commit and branch

Document writes are auto-committed by default. A commit is a content-addressed snapshot: each document version is stored once as a deduplicated blob, so commits share unchanged bytes across history and branches instead of copying collections.

main uses the root .collections tree. Other branches get hidden working trees under .fylo-vcs/branches/, so fylo checkout -b feature isolates subsequent reads and writes without disturbing the base layout. See Version control.

Metadata

Developer-defined key/value data that rides along with a document or file as extended attributes (user.fylo.meta.*), not as fields inside the payload. It survives soft delete, restore, and version-control restore, is snapshotted with each commit, and — on buckets — is indexed and queryable.

Canonical metadata is the derived description FYLO maintains itself: id, createdAt, updatedAt, mtime, plus the file descriptor on buckets. Canonical names win if a custom key collides.

Access descriptor

POSTIX is FYLO's per-record access control, and it is filesystem-native rather than a parallel permission table. A write can bind a POSIX UID, GID, and mode to the record; FYLO applies chown/chmod and stores a portable descriptor in user.fylo.access.

The UID is an authorization claim your application supplies — FYLO does not authenticate it. See Encryption & access.
