Documents & metadata

A document is one JSON file, named by its TTID. Writing one indexes every field; deleting one moves it aside rather than destroying it. This page covers the full lifecycle and the metadata that travels alongside the bytes.

The lifecycle

Collections are created explicitly. Everything else — reads, writes, queries, rebuilds — refuses to operate on a collection that does not exist, so a typo fails loudly instead of silently creating a second store.

patch preserves the TTID. That matters more than it sounds: the TTID is the creation timestamp, the sort order, and the identity used by every index entry, commit, and cursor. An update that changed it would be a delete and an insert wearing a disguise.

Delete is soft

delete moves the payload from docs/ into the hidden sibling .deleted/, keeping the TTID filename. The file's mtime becomes its deletedAt, and it is made read-only (0444). Soft-deleted documents are excluded from ordinary queries. 

{restoreCode}

restore preserves the TTID, moves the payload back, restores writable permissions (0644), rebuilds its index entries, and records the restoration as a live insert event. A tombstoned TTID cannot be written to directly — it must be restored first.

What a document may contain

Scalars, nested objects, and arrays of scalars. Not an array of objects, at any depth. 

{rejectCode}

The rejection is deterministic and happens before any disk work, so it leaves no partial state, and it applies equally to putData, batchPutData, patches, and the in-process API. To model a collection of records, give them their own collection and reference them by key. To keep an opaque payload you will never field-query, serialize it into a single string field.

Metadata

Metadata is stored as extended attributes on the file itself (user.fylo.meta.*), not as fields inside the payload — so it never collides with your document shape and it travels with the bytes across moves. Filesystem-backed stores use native xattrs on macOS and Linux and an NTFS alternate data stream on Windows; browser document collections use a durable OPFS sidecar with identical semantics. 

{metaCode}

Every record includes id, mtime, updatedAt, and createdAt; raw files also include their stored file descriptor. Canonical fields take precedence if a custom key uses the same name.

Keys are 1–64 characters of letters, digits, ., _, or -, starting with a letter or digit. Each value must be JSON-serializable and at most 60 KiB after UTF-8 JSON encoding. A top-level null is a deletion marker, not a storable value. FYLO validates the whole mutation before writing and rolls the xattr batch back if a later write fails.

The fluent put(id, doc).metadata(...) form belongs to the native JavaScript and browser facades. Binary-backed shims expose the same behaviour as getMeta and setMeta, with language-appropriate casing. All surfaces use the same machine operations — no shim invents a second metadata store or merge policy. 

{metaMachineCode}

On filesystem-backed JSON documents metadata is per-version, because a patch writes a new version file. The low-level helpers getXattr, setXattr, listXattr, and removeXattr are exported for raw byte-level access.

Loading data in bulk

Bulk operations coalesce their version-control snapshot: each records a single commit covering every document it touched, instead of one commit per document. Prefer them over a loop of single writes for any real ingest. 

{batchCode}

import from a URL is for trusted sources. Its SSRF guard blocks private addresses and caps the body at 50 MiB, but it is not a safe target for user-supplied URLs.
