Querying & SQL

A query narrows through the prefix index first and hydrates only the documents that matched. The same engine answers both the operator API and SQL, so choosing between them is a matter of taste rather than capability.

Operators

Conditions inside one $ops entry are ANDed; separate entries are ORed. Nothing needs declaring up front — every field of every document was indexed as it was written.

Which index each operator uses

Worth knowing before you design a hot path: three of these can fall back to a full scan, and one of them verifies after hydrating.

Operator Index used Fallback
$eq Exact match key (eq) —
$gt $gte $lt $lte Sortable numeric key (n/nr) Full scan if non-numeric
$contains Exact match on array members —
$like 'ali%' Forward prefix (f) Full scan
$like '%ice' Reversed prefix (r) Full scan
$like '%lic%' Trigram (g3) → hydrate → verify Full scan

SQL

SQL is a front-end over the same collections and the same indexes — a table is a collection. Tagged-template parameters are bound, never interpolated into the statement text.

UPDATE and DELETE are atomic within their collection: either every matched document, its xattrs, and its index entries commit, or the statement restores all before-images.

Pagination

Over the machine protocol, findDocs and findDeletedDocs support bounded continuation on a persistent loop, so a large result never has to fit in one response frame. 

{pageCode}

The result is items, nextCursor, and page. The first request materializes an immutable, disk-backed process-scoped snapshot ordered by TTID binary text, so concurrent mutations cannot duplicate or skip entries.

Cursors are scoped to the operation, collection, query, and access identity. They expire after 15 minutes and become invalid when the loop exits. On EINVALIDCURSOR or a child restart, discard partial state and restart from page one — resuming is not safe.

Snapshot state is private to the native process, released on completion, expiry, or shutdown, and capped at 1 GiB.
