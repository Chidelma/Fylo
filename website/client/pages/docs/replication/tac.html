Backup & sync

FYLO reads and writes one local filesystem root. It does not embed an object-storage client. Mounting, snapshots, replication, and off-site backup therefore stay visible infrastructure choices instead of becoming a second storage engine.

Post-write hooks

Source integrations can receive a notification after a local write or delete has committed. A hook may enqueue work, invalidate application state, or notify an infrastructure-owned replication service; it is not part of FYLO durability.

Hooks are configured by the process embedding FYLO. Shim clients drive the filesystem-only binary and cannot pass functions across the machine protocol. 

{hooksCode}
ModeBehaviour
await-syncWaits for the hook and reports its failure after the local commit.
fire-and-forgetReturns after the local commit and runs the hook in the background.

Back up the filesystem root

Stop the writer or use a filesystem snapshot that provides an atomic point-in-time view, then copy the entire root. Do not independently copy collection directories while writes continue: the catalog, transaction generation, indexes, metadata, and version history must describe the same instant. 

{snapshotCode}

Preserve extended attributes on POSIX and alternate data streams on NTFS. A copy tool that preserves only file bytes can lose UID/GID/mode descriptors, custom metadata, raw-file keys, and checksum stamps.

Restore and verify

  1. Stop all writers and preserve the failed root without modifying it.
  2. Restore the snapshot into a new, empty local directory.
  3. Restore native metadata using a platform-capable copy tool.
  4. Run fylo verify <collection> --root <restored-root> for every collection.
  5. Open the restored root under one exclusive owner before switching traffic.

Never merge a backup into a live root and never let the verification process race a writer. Restore-to-new-root keeps rollback possible and makes incomplete copies obvious.

Remote mounts

FYLO can use a mounted filesystem only when that mount preserves the locking, atomic rename, durability, timestamp, and native metadata guarantees documented for the local platform. Network shares and synchronized folders are unqualified until tested against the full crash and ownership matrix.
