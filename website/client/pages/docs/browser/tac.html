Browser & Explorer

The browser client is local-only. Its JavaScript storage host follows FYLO's logical model and uses a Rust/Wasm kernel for portable index work. It reads and writes a store owned by that browser; there is no backend or network protocol.

Loading the engine

Add the version-pinned loader to the document head:

{loaderCode}
{useCode}

Use the version/latest/ path to track the newest successful release. Direct ESM consumers can import fylo-web.mjs from the same pinned directory instead.

The loader is executable code with this page's origin authority, including access to the origin's FYLO data. Production applications should use the immutable version URL; reserve the mutable version/latest/ alias for a controlled upgrade policy.

For higher assurance, download the loader and every adjacent module, worker, and Wasm asset from the matching release, verify them against SHA256SUMS, and serve them from your own origin. Restrict script, module, worker, and asset origins with CSP. Integrity on the loader alone does not cover modules it imports dynamically.

Mobile clients — iOS/Swift, Android/Kotlin, and Flutter — host this same engine in a WebView, so everything on this page applies to them too.

The engine itself in the browser

The JavaScript host below reimplements FYLO's logical model, which is why the browser has lagged the native engine on version control, schema, and encryption. fylo-browser.wasm replaces it with the engine itself: the same Rust that runs natively, owning browser storage through a table of plain C functions the embedder fills — filesystem, entropy, clock, and a diagnostic channel. It imports no binding-generator glue, so a Swift, Kotlin, or Dart embedder fills the same slots.

OPFS is only half synchronous: file reads and writes are, but every directory operation returns a promise, and the engine calls its host synchronously. So a bridge worker owns every OPFS handle and the engine worker blocks on it through a SharedArrayBuffer — the design sqlite-wasm uses. That needs the page to be cross-origin isolated (Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp), or SharedArrayBuffer does not exist and the worker says so rather than failing as a disk error.

A root's single writer is a Web Lock held for the session, which is what the handshake leaves to the host by reporting exclusiveRoot: false. Verified storing and querying documents over real OPFS in Chromium and Firefox; the JavaScript host below remains the shipped default until it clears the same recovery and soak gates.

Wasm index scanning

The browser index scanner has an opt-in Wasm prototype. It keeps the existing OPFS snapshot and WAL format: Wasm scans the immutable snapshot inside the worker while JavaScript applies live WAL additions and removals, falling back automatically if the module cannot load. 

{wasmCode}

Build the adjacent assets with bun run build:web:wasm. Pass wasm an object with a url to override the module location. collection.inspect() reports indexAcceleration as active, fallback, or off. The feature stays opt-in while the integration is benchmarked on representative stores.

Mounting a real folder

Chromium can mount a user-selected FYLO root directly through the File System Access API, so the browser reads the same directory the CLI writes. 

{fsaCode}

Set access: 'overlay' for read-only exploration: reads fall through to the selected directory while generated indexes, journals, and other writes stay in memory. Firefox and Safari do not implement real-folder access.

Fylo Explorer

Explorer is a browser UI over a real FYLO root on your disk — no server, no protocol. Pick the root once in the OS dialog and later visits reopen it automatically. 

{explorerCode}
  • Read-only by default. Reads go straight to the folder; the engine's own writes land in an in-memory overlay, so the root is never modified.
  • Browse and query. A sidebar split into Collections and Buckets, a document list, a JSON viewer, and a filter bar that accepts SQL WHERE expressions. Buckets browse as Finder-style Miller columns built from the key index, with image preview and byte download. A SQL console runs SELECT statements read-only.
  • Writes are opt-in. "Enable writes" re-arms the folder as readwrite and drops the overlay. Bucket uploads write bytes and a key index entry immediately, but a browser cannot set the key and checksum xattrs — a desktop rebuild or verify re-derives them.

There is no cross-process locking from a browser. A banner warns when the root has live lock files, but concurrent writes are last-writer-wins.

Explorer rejects oversized work before reading it into memory: previews are capped at 32 MiB, imports at 16 MiB and 10,000 records, exports at 64 MiB and 10,000 records, and bucket uploads at 64 MiB. Use the CLI for anything larger.

Self-hosting Explorer

Every release includes a versioned, checksum-covered fylo-explorer-<CalVer>.zip. Extract it into the root of a static host — index.html is at the ZIP root. 

{zipCode}

Production hosts should use a dedicated HTTPS origin, serve the extracted tree at /, and preserve the generated MIME types — especially application/wasm.

Serve Explorer from an origin that hosts no unrelated application code. A CSP limits what a compromised page can load, but browser directory-handle grants and origin storage are shared by every script on the same origin, and the application cannot enforce that separation in code.

Tachyon's generated component runtime currently uses eval for bindings and event dispatch, so the deployment CSP must retain unsafe-eval until Tachyon offers a CSP-safe compiler mode. FYLO's own runtime import uses neither eval nor new Function.
