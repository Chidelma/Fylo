Limitations

What FYLO does not do, stated plainly. Most of these are consequences of the filesystem-first design rather than gaps waiting to be filled — knowing them early is cheaper than discovering them in production.

LimitationDetail
{row.title}{row.detail}

There is no remote access

By design. FYLO has no server and speaks no network protocol. Every client owns its database directly: the CLI and language shims drive the binary against a local root, and the browser and mobile clients embed the engine over an on-device store.

If a root must be reached from another machine, that is a filesystem-layer concern — a mounted volume or a synced directory — and it inherits that layer's consistency guarantees, which are usually weaker than the ones FYLO assumes. The supported storage targets are local POSIX filesystems and NTFS.

Where the guarantees hold

Crash recovery is release-gated on local macOS and Linux filesystems and on native x64 Windows over NTFS. POSTIX access control requires a POSIX host — it is not a Windows authorization boundary, and browser, Explorer, and WebView clients cannot enforce it at all. The exclusive root lease is a kernel lock and is unsupported on network, clustered, and object-backed filesystems.
