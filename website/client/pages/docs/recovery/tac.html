Recovery & rebuild

Documents are truth; indexes are derived. That single rule is what makes recovery tractable — the worst case for a corrupted index is a rebuild, not data loss. This page covers what happens when a process dies mid-write, how to read the state afterwards, and when to intervene.

Rebuilding an index

Run this after operator-level recovery, or whenever an external process has modified data files directly — FYLO cannot see writes it did not make. 

{rebuildCliCode}

A rebuild also repairs bucket files whose key xattr was stripped by a copy tool, restoring each to its default key and emitting file.key-repaired.

The transaction journal

Ordinary collection writes use a logical journal kept outside the collection tree, so it is never mistaken for a document, indexed, or versioned. 

{journalCode}

If a process dies before the commit marker, recovery restores document bytes, file modes, mtimes, xattrs, and the event-journal offset, then rebuilds the derived index. If it dies after the marker, recovery keeps the committed files and completes publication of the stable generation.

Version-control restore and merge use a separate durable transaction under .fylo-vcs/staging/. VersionRepository.init() recovers interrupted transactions before collection bootstrap. Multiple processes may initialize concurrently: one recovery owner does the work while the others wait and then observe the recovered tree and ref.

Reading the state

Inspect a collection without opening journal files by hand:

{statusCode}

state and generation come from the durable collection-generation record; transactionId is also present while that record is writing. activity reports the latest rollback or startup recovery this FYLO instance observed — rolling-back, recovering, idle, or failed — with transaction, operation, phase, timestamps, and failure detail where available. A malformed durable record returns state: 'corrupt' with a detail field.

Treat these three as an operator incident: writing when no collection transaction is in flight, corrupt, or activity.status === 'failed' after initialization.

Stop writers, preserve the root, inspect the emitted error, then repair the filesystem or restore a verified backup. Do not hand-edit the journal or the generation record.

Events to alert on

Configure onEvent to forward recovery lifecycle events:

  • transaction.rollback.started|succeeded|failed — rollback in the process that attempted the operation.
  • transaction.recovery.started|succeeded|failed — reopening an interrupted journal. phase: 'active' rolls back; phase: 'committed' rolls forward.
  • index.rebuilt — the derived index was regenerated during rollback or recovery.

Alert on every .failed event and record elapsed time from the paired timestamps. Event handlers are best-effort observability hooks, not a durable audit log: FYLO catches handler failures so monitoring code cannot break a storage operation.

Where the crash contract holds

The contract is release-gated on local macOS and Linux filesystems and on native x64 Windows over NTFS. On Windows, kernel-owned LockFileEx claims are released when a process dies, and recovery uses directory handles while rejecting junction and reparse-point traversal before any rename or deletion.

This does not extend to arbitrary network shares, sync folders, or filesystems without local atomic link and rename semantics. Those are not supported storage targets.
