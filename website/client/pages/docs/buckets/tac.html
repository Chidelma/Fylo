Buckets & raw files

A bucket stores bytes instead of records. It is the same engine, the same index, and the same API as a document collection — only the value type differs. What you gain is a queryable, checksummed object store that lives in a plain directory.

Creating and reading

Create the collection with kind: 'file', then pass a Blob, File, or URL to the ordinary put().

The fluent byte accessors below belong to the browser facade. Binary-backed shims read the same bytes through the machine protocol — see Language clients. 

{basicCode}

FYLO stores the bytes unchanged and retains no source path or URL: 

{pathCode}

The metadata it derives — name, key, extension, contentType, contentLength, etag, checksumSHA256, createdAt, and lastModified — goes through the normal prefix index, so all of it is queryable with find().

Databases written by older FYLO versions, where file collections lived under .collections/, migrate to .buckets/ automatically the first time the engine opens them.

Logical keys

A key is object-style logical metadata, not a filesystem path — the bytes still live under the TTID filename. Keys are unique among active files in a collection, always begin with /, may be at most 1024 UTF-8 bytes, and cannot contain backslashes, control characters, or . / .. segments. 

{keysCode}

The default key is /. Root and trailing-slash keys append the generated TTID filename; an exact key is preserved as supplied. The key is stored as a user.fylo.key extended attribute on the file, so it moves with the bytes.

Folders

Keys can be reassigned in place — no byte rewrite — and the folder tree they imply can be browsed one level at a time. 

{folderCode}

folder() reads only key metadata for deeper descendants (one xattr each), so browsing stays cheap in large trees.

Checksums and the integrity audit

Checksums are cached in a user.fylo.checksum xattr stamped with the file's size and mtime, so listings and reads never re-hash contents. The hash is recomputed automatically whenever the stamp stops matching.

The cache trusts its stamp — which means silent corruption that preserves both size and mtime is invisible to the fast path. verify() is the stamp-ignoring audit that closes the gap. It re-hashes the full contents of every file, active and soft-deleted, freshens matching stamps, and reports mismatches without touching the corrupt file's original claim. 

{verifyCode}

Each mismatch also emits a file.checksum-mismatch event through onEvent. The audit reads every byte, so it is slow by design — run it as a scheduled job, never per request. The CLI equivalent exits non-zero when corruption is found, so a cron line is a complete weekly audit: 

{cronCode}

Machine-protocol callers use {"op": "verifyCollection", "collection": "assets"}.

Developer metadata is indexed

On buckets, metadata is returned inside each manifest (manifest.meta) and is indexed, so it can be queried — including numerically. 

{metaQueryCode}

Metadata survives soft delete, restore, and version-control restore. If a store is ever copied by an xattr-dropping tool, rebuild() repairs each stripped file to its default /<filename> key and emits a file.key-repaired event — custom keys are not recoverable from bytes alone, so use a version-control restore when you need full fidelity.

Ingestion limits

URL ingestion snapshots the content at write time. file: URLs work server-side; browser runtimes accept Blob, File, and network URLs. The default limit is 50 MiB and can be raised per write with { maxBytes: 250 * 1024 * 1024 }.
